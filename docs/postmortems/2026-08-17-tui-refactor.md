# 复盘：TUI 上帝类拆分与收益递减停止点

- **日期**：2026-08-17
- **类型**：结构优化
- **状态**：五阶段拆分完成，刻意未追逐“单文件 <500 行”原目标

## 背景

TUI 是 CodeRook 的主要产品面，但 `tui/app.py` 一度约 4,176 行，同时承担控件、连接重试、slash
命令、IPC 调用、事件渲染和 App 编排。新增管理面板会同时碰到协议、连接、渲染和状态，评审边界不清，
也容易在重构中混入行为变化。

## 方案与实施

重构被拆成五个可独立回退的阶段：

1. 控件迁入 `tui/widgets/`；
2. 连接、重连和会话恢复迁入 `tui/connection.py`；
3. slash command 从约 360 行条件链改为数据驱动注册表 `tui/commands.py`；
4. IPC timeout/错误统一到 `tui/ipc_actions.py`；
5. 事件族渲染迁入 `tui/render.py`，管理面板集中在 `tui/panels/`。

每阶段只做等价迁移，独立提交，不顺手修业务缺陷；Textual test driver 和既有交互语义作为保护网。
拆分完成时 `app.py` 从约 4,176 行降至约 2,110 行，随后加入管理功能后约 2,246 行；阶段新增 95 个
TUI/管理/补全相关测试。

## 未达到的目标与停止理由

原计划希望单文件低于 500 行，实际没有达到。剩余部分主要是 Textual App 编排、状态和一次性用户流程，
继续机械拆分会引入大量跨对象转发和生命周期同步，却不能按同等比例降低修改风险。

因此停止条件从“行数达标”改为三个用户/维护结果：新命令可以由声明 + handler 接入，连接错误有统一语义，
事件渲染可以按族测试。这里选择承认指标偏差，而不是为了完成计划制造空壳类。

## 收益与不能推导的结论

已证实的收益：职责边界更清晰；管理面板通过 typed IPC 而非直读 daemon 状态；slash command 查找和参数
补全可以独立测试；重连、IPC 错误和事件渲染各自有回归保护。

不能从行数和测试数推导“缺陷降低 X%”“性能提升 X%”或“开发效率提升 X%”，因为没有重构前后的
同口径缺陷率、交付周期或 profile。简历只使用代码规模变化解释重构范围，并用 95 个测试说明保护手段。

## 后续规则

- TUI 新管理能力优先放入 commands/ipc_actions/render/panels 的现有边界；
- 只有出现明确共同变化原因时再抽象，不以文件行数单独触发重构；
- UI 行为改动附确定性 Textual 测试或截图，结构迁移与功能修复分开提交；
- 每次优化同时记录原目标、实际出口和无法证明的收益。
